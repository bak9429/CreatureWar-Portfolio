# 주요 설계 의사결정

## 1. 클래스를 고정하지 않는 이유

**문제:** 종족에 '전투형만 가능' 같은 잠금이 있으면 플레이어가 개성적인 생물을 만들기 어렵습니다.  
**결정:** 모든 종족에 다양한 역할 가능성을 열어두고, 성능과 실제 행동 수단을 PART/ORGAN의 조합으로 구분.  
**장점:** 동일 종족에서도 정찰+공병, 전투+보급 등 하이브리드 설계 허용.  
**남은 검증:** 유효 조합 폭이 넓어지는 만큼 밸런스와 공급/COST 제약 검증이 필요.

## 2. T3 역할을 T2 뒤에서 공통 분기시키는 이유

**문제:** T2의 동물 계통마다 전술 역할을 별도 중복 생성하면 데이터 유지 비용이 급증.  
**결정:** T2 계통을 고른 뒤 **공통 T3 9개 역할 → 역할당 T4 4개 방식**으로 이동.  
**장점:** 생물 계통과 역할을 독립적인 관심사로 관리.  
**주의:** 공통 노드를 재사용해도 실제 T5 외형은 선택한 T2 계통의 해부학적 정체성을 유지해야 함.

## 3. 플레이어 지휘와 개체 AI의 분리

**문제:** 전부 자동으로 움직이면 RTS의 지휘 경험이 약하고, 모든 생물을 개별 조작하면 대규모 전투에서 부담이 과도함.  
**결정:** 플레이어는 분대 진형·이동·우선표적·정찰·건설을 지정하고, AI는 공격수단 선택, 사거리 조정 및 세부 동작 처리.  
**남은 검증:** 대규모 유닛 환경에서 성능과 명령 일관성.

## 4. 모델 품질 판정과 생성 성공을 분리

**문제:** AI가 GLB를 생성하는 것 자체가 해당 생물의 정확한 형태, 다리 수, 목 접합부, 파츠 교체 가능성을 증명하지 않음.  
**결정:** 이미지 단일 개체성 → GLB 생성 성공 → 해부학/실루엣 → BODY/HEAD 접합 → 엔진 임포트 순서로 검수.  
**남은 검증:** 종족 전체의 노드별 3D 결과에 대한 일관된 품질 게이트.
